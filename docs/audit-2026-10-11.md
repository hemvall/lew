# Audit Lew — 11 octobre 2026

## Objectif
Faire de Lew un espace quotidien simple : concevoir un produit, préparer une mission, suivre son travail et relire sa livraison. Deux apps suffisent : Travail et Product Lab.

## Périmètre et méthode
Lecture des parcours frontend, du serveur, de l'orchestration et des tests. Base isolée : commit 27f04d0, avec comparaison du checkout utilisateur. Aucun accès à des données privées, aucune migration ni déploiement.
Les changements locaux de missions.mjs, app.js, mission-ui.js, os-windows.css/js, studio-model.js/ui.js et docs/briefs sont conservés dans le checkout utilisateur et ne sont pas inclus dans cette PR. Ils comprennent déjà l'import Markdown et le transfert du brief : ce lot ne les réimplémente pas.

## Constats étayés
| Constat | Preuve | Conséquence |
|---|---|---|
| Deux apps et navigation par fenêtres sont déjà en place | public/os-model.js, os-windows.js | Garder cette structure, éviter une nouvelle app pour chaque service |
| Product Lab cadre 24 décisions et exporte le brief | public/studio-model.js | Une base utile pour créer des missions |
| Le transfert automatique existe uniquement dans les changements locaux | diff de studio-ui.js, app.js et mission-ui.js | Tester ce parcours lors de leur intégration, sans écraser le travail |
| Les erreurs de processus restent opaques | mission-routes.mjs lance authWorker; mission-adapter.mjs lance Git sans diagnostic préalable | spawn EPERM ne dit pas comment reprendre |
| Aucun contrôle Git avant création d'une mission | mission-routes.mjs POST /missions | Une mission peut être persistée puis bloquée immédiatement |
| Les vérifications de livraison sont substantielles | missions.mjs exige des commandes réussies et vérifie le SHA | Préserver ces garanties |
| Les missions sont sérialisées sur le worker | missions.mjs queue/running | Rendre l'attente visible avant de promettre du parallélisme |
| La récupération reste explicite après redémarrage | MissionEngine.performRecovery | Bon principe; afficher le prochain geste à l'utilisateur |
| La documentation du Studio et la liste de checks sont en retard | README parle de sage; package check omet studio/os | Facilite les régressions UI |

## Premier lot : worker prêt avant lancement
1. Ajouter un diagnostic borné des exécutables Git et Codex, sans shell ni exposition de stderr.
2. Afficher le résultat dans la confirmation de mission avec un bouton de nouvelle vérification.
3. Refaire le contrôle côté serveur lors du POST, avant création.
4. Préserver le formulaire en cas d'échec; ne lancer aucune mission réelle dans les tests.
5. Couvrir permissions, executable absent, délai dépassé, erreur imprévue et refus de création.

## Limites
Ce contrôle ne vérifie pas les droits du repo distant, la qualité du brief, la disponibilité du modèle ou les quotas. La connexion au compte est contrôlée ensuite par le parcours existant. Un programme --version peut fonctionner alors qu'un app-server échoue; son erreur conserve la prise en charge existante. Le contrôle n'élève aucune permission et ne contourne pas le sandbox.
